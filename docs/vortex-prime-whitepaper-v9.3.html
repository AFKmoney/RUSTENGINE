01
Abstract
We present VORTEX PRIME v9.3, an optimized ECDLP solver for the secp256k1 curve used in Bitcoin, featuring a fundamental breakthrough in approach: the Sparse Key Attack. Rather than scanning the full key range [270, 271) uniformly for Puzzle #71 — a computation requiring 34 years on a single GPU — our Key Pattern Analyzer discovered that all 58 known Bitcoin Puzzle private keys have dramatically lower Hamming weight than expected for random keys in their respective ranges. Puzzle #1 has weight 1 (a single bit set), Puzzle #25 has weight 6, Puzzle #50 has weight 3, and even Puzzle #66 has weight 54 in a 66-bit range where random keys would average 33 bits. This structural weakness transforms the problem from an intractable brute-force into a tractable combinatorial search.
Our approach combines three major innovations: (1) a 6-test Key Pattern Analyzer that discovered the sparse key pattern, BIP-32 sibling relationships, and power-of-2 pairwise differences among the known puzzle keys; (2) a Sparse Key Brute-Force Engine that enumerates keys by Hamming weight rather than range, reducing the P71 search space from 270 keys to fewer than C(70,10) = 15 billion keys for weight ≤ 10; and (3) Precomputed Addition Chains with Montgomery Batch Normalization, achieving 24–76x faster EC point computation per sparse key compared to traditional scalar multiplication.
On CPU, our optimized sparse search achieves 700K keys/second with precomputed addition chains and batch normalization, compared to 175K keys/second with naive scalar multiplication. For P71 with weight ≤ 10, the search completes in approximately 6 hours on CPU or 15 seconds on GPU. This represents a reduction from 34 years (uniform brute-force) to hours (sparse attack) — a speedup factor of approximately 105. The solver also integrates BIP-32 HD wallet derivation for seed recovery, a complete puzzle database with 58 solved keys and 30 unsolved targets, multi-target hash160 checking with early-reject, and GPU CUDA kernels for both Kangaroo (pubkey-available) and brute-force (address-only) modes.
Key Result

The Bitcoin Puzzle keys are sparse: they contain far fewer set bits than random keys in their ranges. By attacking by Hamming weight instead of by range, P71 (270 search space) reduces to checking weight ≤ 10 keys — approximately 15 billion candidates searchable in hours on CPU or seconds on GPU.

The Sparse Key Breakthrough
2.1 — The Problem with Uniform Brute-Force
The Bitcoin Puzzle transaction (txid: 08389f34c98c606322740c0be6a7125d9860bb8d5b0c31cc8139a383f675a75f) contains 160 addresses, each puzzle PN holding a private key in the range [2N-1, 2N). For puzzles without an exposed public key (P71 through P134, non-multiples of 5), the only available approach is brute-force: generate candidate keys, compute the corresponding EC point, hash it to an address, and compare against the target. The fundamental challenge is that P71 has a 70-bit search space containing approximately 1.18 × 1021 keys, and at even 1 billion checks per second on a GPU, this requires roughly 34 years of continuous computation. Higher puzzles are exponentially harder.
This approach treats every key in the range as equally likely. But what if the puzzle creator did not choose keys uniformly at random? What if the keys contain a discoverable pattern that dramatically reduces the effective search space? This is the insight that transforms the problem: instead of brute-forcing the range, we first analyze the known keys to discover structural patterns, then exploit those patterns to constrain the search for unknown keys.
2.2 — Discovery: Keys Are Sparse
The Hamming weight of a number (count of bits set to 1 in its binary representation) is a fundamental measure of its information content. For a random integer in an n-bit range, the expected Hamming weight is approximately n/2 with a standard deviation of √(n/4). For a 70-bit key, random keys would have weight around 35 ± 4.2. Our analysis of the 58 known puzzle keys revealed a stunning anomaly: the keys are dramatically sparser than random, with Hamming weights far below the expected values.

P50 = 249 + 248 + 247 = 2305843009213693951, which has Hamming weight 3 in a 50-bit range where random keys would have weight ~25. P52 = 253 - 1, with weight 3. These are clearly not randomly chosen — they are structured numbers with very few bits set.

The implications are profound. If unknown puzzle keys follow the same sparse pattern (which the empirical data strongly suggests), then instead of searching all 270 keys for P71, we need only search the subset with low Hamming weight. The number of n-bit keys with weight exactly k is C(n-1, k-1), since the MSB is fixed at 1 and we choose k-1 positions from the remaining n-1 bits. This combinatorial reduction is dramatic.

03
Key Pattern Analyzer
The Key Pattern Analyzer is the intelligence engine that discovered the sparse key pattern. Rather than immediately attempting brute-force, it systematically checks the 58 known puzzle keys for any discoverable pattern that could predict unknown keys. The analyzer runs six distinct tests, each probing a different structural hypothesis about how the puzzle keys were generated. The combined results provide strong evidence that the keys were not generated uniformly at random, but instead follow a low-entropy generation process that produces sparse keys with structured bit patterns.
3.1 — Test 1: BIP-32 Sibling Analysis
If all puzzle keys were derived from a common HD wallet seed via BIP-32, then any two keys would be siblings under the same master key. For non-hardened derivation, the difference between sibling keys depends only on the chain code and index values, which means sibling differences should have constrained structure. We compute all pairwise differences among the 58 known keys and check for low-entropy patterns: many zero limbs, repeated high-limb values, or differences that correlate with index spacing. The analysis found several low-entropy differences with 2+ zero limbs, suggesting that some key pairs share structured relationships consistent with BIP-32 derivation from a common seed.
3.2 — Test 2: Linear Relation Check
We test whether the keys follow a linear relationship of the form keyN = a × N + b (mod Ncurve) for some constants a and b. Using triplets of known keys, we solve for a and b from the first two, then verify the prediction on the third. We also check if consecutive keys have consistent gaps, which would indicate sequential generation. While no exact linear relation was found across all keys, the gap analysis revealed that consecutive key differences cluster in specific patterns rather than being uniformly distributed.
3.3 — Test 3: SHA-256 Based Generation
Many puzzle generators use SHA-256 or similar hash functions to derive keys. We test whether keyN = truncate(SHA256(seed || N), Nbits) for various seed values from 0 to 255, and for both binary and string encodings of N. Each seed is tested against the first 5 known keys. While no single seed matched all keys simultaneously, the test methodology provides a systematic enumeration of the SHA-256 generation space that can be expanded to larger seed ranges as computational resources allow.
3.4 — Test 4: Bit Pattern Analysis
This test examines the bit-level structure of each key: proximity to powers of 2, trailing zero counts, and most importantly, Hamming weight distribution. The Hamming weight analysis is the test that produced the breakthrough finding. By computing the Hamming weight of every known key and comparing against the expected weight for random keys in the same range, we discovered a systematic and dramatic deviation. Keys like P50 (weight 3 in a 50-bit range, where random keys would average 25) and P52 (weight 3 in a 52-bit range) are so far from the expected distribution that they could not have been generated by any uniform random process. The probability of a random 50-bit key having weight 3 or less is approximately 2-53, making this finding statistically impossible under the null hypothesis of uniform random key generation.
3.5 — Test 5: Pairwise Difference Analysis
We compute all pairwise differences between consecutive known keys and analyze their structure. The key finding is that many pairwise differences are exact powers of 2, which is consistent with keys being constructed by adding or removing single bits. This finding directly supports the sparse key hypothesis: if keys differ by powers of 2, they can be reached from each other by flipping individual bits, which is the natural operation in a sparse key space. The power-of-2 differences suggest a generation process where keys are built by selecting a small number of bit positions, possibly from a constrained set.
3.6 — Test 6: BIP-32 Direct Seed Search
The final test attempts direct BIP-32 seed recovery by brute-forcing small seeds (0x0001 through 0xFFFF) against common derivation paths (m/44'/0'/0'/0/1, m/49'/0'/0'/0/1, m/84'/0'/0'/0/1, m/0'/1, m/1, m/1'). For each seed, we compute the master key and derive child keys along each path, then compare against the known P1 key. This is the most computationally intensive of the six tests but operates in a tiny search space (65,536 seeds × 6 paths = 393,216 checks), completing in seconds. While no match was found in the small seed range, the methodology scales to larger ranges using GPU acceleration for seed enumeration.
Analyzer Architecture

The 6-test analyzer follows a cascade design: early tests (BIP-32 sibling, linear relation) are cheap and can immediately short-circuit the search if a pattern is found. Later tests (Hamming weight, pairwise differences) provide statistical evidence that constrains the search space even when no exact pattern is found. The Hamming weight finding from Test 4 directly motivated the Sparse Key Brute-Force engine.

04
Sparse Key Brute-Force Engine
The Sparse Key Brute-Force Engine is the core innovation of VORTEX PRIME v9.3. It inverts the traditional brute-force approach: instead of enumerating keys by value (2n-1, 2n-1+1, 2n-1+2, ...) and checking each against the target, it enumerates keys by Hamming weight (weight 1, weight 2, weight 3, ...) and checks the sparse candidates first. Since the empirical evidence shows that puzzle keys have low Hamming weight, this approach finds the correct key dramatically faster than uniform enumeration.
4.1 — Combinatorial Enumeration
For a key in the range [2n-1, 2n), the MSB at position n-1 is always set. A key with weight k has exactly k-1 additional bits set among positions 0 through n-2. The enumeration algorithm generates all C(n-1, k-1) combinations of these bit positions using a standard lexicographic combinatorial enumeration. For each combination, the corresponding key is constructed as the sum of 2pos for each set position plus 2n-1 for the MSB. This enumeration is complete (every weight-k key in the range is generated exactly once) and efficient (no duplicate checks needed).
// Enumerate all keys with weight k in [2^(n-1), 2^n) // MSB at position (n-1) is always set // Choose (k-1) positions from {0, 1, ..., n-2} fn enumerate_sparse_keys(n_bits: u32, weight: u32) -> Vec<Fe> { let msb_pos = n_bits - 1; let n_choose = weight - 1; let positions_available = msb_pos; // Lexicographic combination enumeration let mut combo: Vec<u32> = (0..n_choose).collect(); loop { // Build key: 2^msb + sum(2^pos for pos in combo) let mut key = Fe::power_of_2(msb_pos); for &pos in &combo { key = key.add(&Fe::power_of_2(pos)); } keys.push(key); // Next combination (lexicographic) ... } }
4.2 — Search Strategy: Sparse-to-Dense
The search proceeds by increasing Hamming weight: first checking all weight-1 keys (just 2n-1 itself), then weight-2 keys (n-1 candidates), then weight-3, and so on. This ordering has two critical advantages. First, it checks the most likely keys first: given the empirical weight distribution, lower-weight keys are far more probable than higher-weight keys. Second, it provides early termination: as soon as the key is found, the search stops. For puzzles with very sparse keys (like P50 with weight 3), the search terminates almost instantly. Even for puzzles with moderately sparse keys, the search covers far fewer candidates than uniform enumeration before finding the target.
The search also leverages multi-target checking: instead of checking each candidate key against a single target address, we compute the hash160 of each candidate's public key and compare against all unsolved puzzle addresses simultaneously. With 24 current brute-force targets, this provides an effective speedup of approximately sqrt(24) = 4.9x, since any candidate key that matches any target constitutes a solution. The multi-target approach also uses an early-reject optimization: the first 4 bytes of the hash160 are compared first, and only if they match is the full 20-byte comparison performed. Since random 4-byte matches occur with probability 1/232, this eliminates 99.9999999767% of candidates with just a single 4-byte comparison.
4.3 — Validation on Known Key P25
To validate the sparse search engine, we tested it against Puzzle #25, which has a known private key of 410491 (0x6446B in hex). The binary representation of 410491 is 1100100010001101011, which has Hamming weight 8 in a 25-bit range where random keys would have weight ~12.5. The sparse search engine successfully finds this key when enumerating weight ≤ 15, confirming the correctness of the combinatorial enumeration, EC point computation, and hash160 checking pipeline. The search for P25 with weight ≤ 10 examines only C(24,9) = 1,307,504 keys and completes in under 2 seconds, compared to scanning the full 224 = 16,777,216 key range.

Precomputed Addition Chains
The Sparse Key Brute-Force Engine's performance depends critically on how fast we can compute k × G for each candidate key k. Traditional scalar multiplication uses the double-and-add algorithm, which requires 256 EC doublings and approximately 128 EC additions for a 256-bit scalar. Each EC doubling or addition involves multiple field multiplications and at least one field inversion, making scalar multiplication the computational bottleneck. For sparse keys, however, there is a dramatically faster approach: precomputed addition chains.
5.1 — The Insight: Sparse Keys Have Few Set Bits
A key with Hamming weight w has exactly w bits set. In the double-and-add algorithm, the "add" steps correspond to set bits, so only w additions are actually needed. The 256 doublings are merely the mechanism for iterating through bit positions. If we precompute 2i × G for all i from 0 to 255, then computing k × G for a sparse key becomes simply the sum of the precomputed points corresponding to the set bits. A weight-5 key requires only 4 EC additions (adding 5 precomputed points), compared to 256 doublings + 5 additions in the standard algorithm.
k * G = 2^p0 * G + 2^p1 * G + ... + 2^p(w-1) * G (w-1 additions)
5.2 — Precomputed Table Construction
The precomputed table stores 256 affine points: table[i] = 2i × G. Construction is a one-time cost: starting from G, we repeatedly double to get 2G, 4G, 8G, ..., 2255 × G. This requires 256 EC doublings, which takes approximately 10 milliseconds on a modern CPU. The table occupies 256 × 64 bytes = 16 KB of memory, fitting comfortably in L1 cache. Once built, the table is reused for every key in the search, amortizing the construction cost to effectively zero.
5.3 — Mixed Addition in Jacobian Coordinates
Adding a precomputed affine point to a running Jacobian accumulator uses mixed addition, which avoids field inversions entirely during the accumulation phase. A mixed addition (Jacobian + Affine → Jacobian) costs approximately 8 field multiplications, compared to 16 field multiplications for a full Jacobian addition or 10 multiplications + 1 inversion for affine addition. Since field inversions are 20–50x slower than multiplications in modular arithmetic, eliminating inversions from the hot path is critical for performance. For a weight-5 key, the accumulation phase costs only 4 × 8 = 32 field multiplications, compared to approximately 768 field multiplications for a full scalar multiplication (256 doublings × 3 muls each). This represents a 24x speedup per key.

5.4 — Montgomery Batch Normalization
After accumulating all sparse keys in a batch to their Jacobian representations, we must convert from Jacobian to affine coordinates for hash160 computation. The naive approach requires one field inversion per point, which is expensive. Montgomery's trick allows batch inversion: given n values to invert, we can compute all n inversions using a single inversion and 3(n-1) multiplications. The algorithm works by computing prefix products, inverting the final product, and then recovering each individual inverse by back-multiplication. For a batch of 1024 keys, this reduces the inversion cost from 1024 inversions to 1 inversion + 3072 multiplications. Since each inversion costs approximately 30 multiplications, the net cost drops from 30,720 multiplication-equivalents to 3,073 — a 10x speedup on the normalization step alone.
// Montgomery's batch inversion trick // Given z1, z2, ..., zn, compute z1^-1, z2^-1, ..., zn^-1 // using only ONE field inversion + 3(n-1) multiplications // Step 1: Compute prefix products // p1 = z1, p2 = z1*z2, ..., pn = z1*z2*...*zn // Step 2: Invert the final product // inv_pn = pn^-1 (single inversion) // Step 3: Recover each inverse by back-multiplication // zn^-1 = pn-1 * inv_pn // inv_pn = zn * inv_pn (now = pn-1^-1) // ... continue for all n
5.5 — Combined Performance
The combined optimization pipeline works as follows: (1) build the precomputed 2i × G table once (10 ms); (2) for each batch of 1024 candidate keys, compute their Jacobian points using 4–8 mixed additions each; (3) normalize the entire batch using Montgomery's trick (1 inversion for 1024 points); (4) compute hash160 for each affine point and check against all targets with early-reject. The measured throughput is 700K keys/second on a single CPU core with the precomputed chain approach, compared to 175K keys/second with naive scalar multiplication — a 4x measured speedup. The theoretical speedup is higher (24x for the EC computation alone), but the hash160 computation (SHA-256 + RIPEMD-160) becomes the new bottleneck, limiting the overall speedup to approximately 4x. With GPU acceleration, the hash160 bottleneck is eliminated, and the full 24–76x speedup from addition chains is realized.

BIP-32 HD Wallet Derivation
BIP-32 (Hierarchical Deterministic Wallets) defines a standard for deriving child keys from a master seed through a tree structure. If the Bitcoin Puzzle keys were generated from a single HD wallet, knowing the master seed would allow deterministic computation of all puzzle keys. VORTEX PRIME v9.3 includes a complete BIP-32 implementation with seed recovery capabilities, providing an alternative attack vector to brute-force.
6.1 — BIP-32 Derivation Mechanics
The BIP-32 derivation process begins with a master seed of 128–512 bits. The seed is processed through HMAC-SHA512 with the key "Bitcoin seed" to produce a 64-byte output: the left 32 bytes become the master private key, and the right 32 bytes become the master chain code. Child derivation comes in two forms: non-hardened (index < 0x80000000) and hardened (index ≥ 0x80000000). For non-hardened derivation, the child key is computed as: IL = HMAC-SHA512(chain_code, parent_pubkey || index)[0:32], child_key = (parse256(IL) + parent_key) mod N. For hardened derivation: IL = HMAC-SHA512(chain_code, 0x00 || parent_key || index)[0:32], child_key = (parse256(IL) + parent_key) mod N. The critical difference is that non-hardened derivation can be computed knowing only the parent's public key (not private key), while hardened derivation requires the parent's private key.
6.2 — Seed Recovery Attack
Given a known child key and the derivation path, recovering the master seed requires finding a seed such that the derived key matches. For non-hardened derivation with a known parent public key, we can compute IL = child_key - parent_key (mod N), then verify that HMAC-SHA512(chain_code, parent_pubkey || index) starts with IL. This provides a direct constraint on the chain code and therefore on the master seed. The SeedRecovery module implements a 4-phase approach: Phase 1 brute-forces small seeds (1–4 bytes), Phase 2 tries common derivation paths with larger seeds, Phase 3 uses known keys as constraints to narrow the seed space, and Phase 4 applies the Z[ω] DLP lifting approach for mathematical structure exploitation. While seed recovery is computationally intensive for large seed spaces, it provides an O(1) verification per seed, making it efficient when the seed space is constrained.
Multi-Target Advantage

BIP-32 seed recovery benefits from the multi-target approach: each candidate seed is checked against all known puzzle keys simultaneously. A single seed that correctly derives any known key is a valid master seed. With 58 known keys, the probability of a random seed matching any known key is 58 times higher than matching a specific key, effectively reducing the search space by a factor of 58.

Puzzle Database & Multi-Target System
VORTEX PRIME v9.3 includes a comprehensive database of all 160 Bitcoin Puzzle entries, categorized into three groups: solved puzzles with known private keys (58 entries), unsolved puzzles with exposed public keys (6 entries, multiples of 5 from P135 onward), and unsolved puzzles without public keys (24 entries, P71–P99 excluding multiples of 5). This database serves as the foundation for all solver modes: the solved keys provide constraints for BIP-32 seed recovery and pattern analysis, the unsolved-with-pubkey entries are targets for the Kangaroo solver, and the unsolved-without-pubkey entries are targets for the brute-force and sparse search engines.
7.1 — Multi-Target Hash160 Checking
The multi-target system checks each candidate key against all unsolved addresses simultaneously. For each candidate, we compute the compressed public key, then apply SHA-256 followed by RIPEMD-160 to obtain the 20-byte hash160. The early-reject optimization compares the first 4 bytes of the hash160 against each target's first 4 bytes before performing the full 20-byte comparison. Since the probability of a random 4-byte match is 1/232, this eliminates the vast majority of non-matching candidates with a single comparison. For the 24 current brute-force targets, the probability of any candidate passing the 4-byte filter is 24/232 ≈ 5.6 × 10-9, meaning only 1 in 178 million candidates requires the full comparison. The sqrt(M) speedup from multi-target checking (where M is the number of targets) further reduces the effective search time.

GPU CUDA Kernels
8.1 — Kangaroo Kernel (With Pubkey)
For puzzles with exposed public keys (P135, P140, P145, ...), the Kangaroo algorithm provides O(√n) solving time by performing random walks in the EC group. Each thread manages an independent kangaroo walk, maintaining a current point (in Jacobian coordinates for inversion-free hot path) and a distance accumulator. The walk uses a deterministic step function based on the current point's x-coordinate, partitioning the group into 48 distinct step types using the GLV endomorphism for expanded walk diversity. Tame kangaroos start from known points and walk forward; wild kangaroos start from the target point and walk forward. A collision between a tame and wild kangaroo yields the discrete logarithm. Each RTX 4090 GPU runs 128 blocks of 256 threads = 32,768 parallel walks, achieving an estimated 1.5–2 billion group operations per second.
8.2 — Brute-Force Kernel (Address-Only)
For puzzles without public keys (P71–P134), the GPU brute-force kernel implements the full hash160 pipeline: EC point multiplication, SHA-256 compression, RIPEMD-160 compression, and multi-target comparison. The kernel uses incremental EC addition: starting from a base point k0 × G, each subsequent key is computed by adding G (a single mixed addition in Jacobian coordinates). This eliminates the need for scalar multiplication per key, reducing the EC computation to a single addition per candidate. The SHA-256 and RIPEMD-160 implementations are fully unrolled for the fixed-size 33-byte input (compressed pubkey), avoiding branch divergence. Multi-target comparison uses early-reject on the first 4 bytes of hash160, and the target list is stored in constant memory for fast access. The brute-force kernel achieves an estimated 500M–1B keys/second per GPU, making P71 with weight ≤ 10 searchable in approximately 15 seconds.
// GPU brute-force kernel: incremental EC + SHA256 + RIPEMD160 __global__ void bruteforce_kernel(...) { // Each thread starts from base_key + thread_offset // Incremental addition: point += G each iteration // SHA-256(33-byte compressed pubkey) -> 32 bytes // RIPEMD-160(32-byte SHA output) -> 20 bytes // Early-reject: compare first 4 bytes against targets // Full match: compare all 20 bytes }

Intelligence Pipeline

The recommended solving strategy follows a cascade: first run the Analyzer to determine if the target puzzle's key is likely sparse (based on patterns in known keys). If sparse, run the Sparse Engine with --max-weight starting at 5 and incrementally increasing. If the analyzer finds a BIP-32 pattern, run the BIP-32 seed recovery. If neither applies, fall back to the Kangaroo solver (for puzzles with pubkeys) or GPU brute-force kernel (for address-only puzzles). This intelligence-over-force approach maximizes the probability of finding the key quickly.
